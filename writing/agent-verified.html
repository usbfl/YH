示例文章 · AGENT RESEARCH

让 Agent 的推荐结果
有依据。

以 GameReach 的设计为例，解释“自然语言偏好—候选检索—证据验证—推荐”的区别。

本文为基于项目 README 和简历制作的网站文章示例，适合在实际发布前加入个人经历、截图与实验数据。

1. 为什么仅靠标签不够？

用户说“希望战斗技术性高，但不想花大量时间刷装备”，这不是单一的游戏类型标签。系统需要把它拆成正向偏好、负向偏好以及哪些条件不能违反，再去寻找游戏是否真的具有相应机制。

2. 让需求先变成可检查的条件

GameReach 把用户当前输入与兴趣卡片转换为玩法标签、方向、权重及软硬约束。硬约束不能凭空视为已满足；软偏好缺少证据时，可以保留不确定性，而不是直接排除游戏。

用户表达→结构化条件→候选游戏→证据核验

3. Agent 分工不只是增加模型调用

Planner 负责把目标转为研究任务；Researcher 从目录与玩家评价获取候选和可引用材料；Verifier 检查材料是否支持判断。这样做的价值不是角色数量，而是给每一步设置不同的输入、输出与失败边界。

4. 推荐理由应该能被复查

最终页面不仅展示匹配程度，还应回答“哪些评论支持这个结论”“有没有反例”“哪些条件仍然未知”。系统把关注点放在本次重要的机制上，而不是逼迫每款游戏的所有属性都完成核验。

5. 工程验证不等于真实效果验证

GameReach v0.11.0 的仓库报告了离线测试和浏览器测试，但本轮未运行真实付费模型与实时目录数据。因此评价效果时，需要将工程正确性和真实推荐表现分开。
